# Общие правила для правщиков

Читается вместе с персональным брифом. Персональный бриф главнее, если они расходятся.

## Откуда стартовать

- Ветка-основа: `claude/vigilant-wright-2gtdxe` (в ней аудит и `tools/syncheck.sh`).
- Своя ветка — имя указано в брифе. Пушить только туда.
- Сначала прочитать свой бриф, затем находки по номерам в `audit/*.md`. Остальные находки не трогать.
- Навык проекта: `.claude/skills/fieldsensor/SKILL.md` — прочитать до первой правки.

## Границы

- Править **только файлы из своего списка владения**. Если без чужого файла не обойтись,
  не править его, а записать в отчёт: «нужна правка в X, строка Y, потому что Z».
- Новых `.c` в `Core/Src` не заводить: каталог `Debug/` не в git, и сборка CubeIDE
  у владельца новый файл не увидит. Новая чистая логика оформляется как `static inline`
  в новом заголовке `Core/Inc/<что-то>_policy.h` и тестируется из `tests/test_main.c`.
- Код, сгенерированный CubeMX, менять только внутри `/* USER CODE BEGIN ... */ ... END`.
- Стиль — как вокруг: комментарии по-русски, объясняют «почему», а не «что».
- Ничего не форматировать заново, не переименовывать «заодно», не чинить чужие находки.

## Критерий готовности (проверяется командами)

1. `sh tools/syncheck.sh` → `syncheck: OK`.
2. Хостовые тесты собраны и проходят, провалов 0:
   ```
   mkdir -p build/tests && gcc -std=c11 -Wall -Wextra -ICore/Inc -o build/tests/t \
     tests/test_main.c Core/Src/aht20_decode.c Core/Src/ds18b20_decode.c \
     Core/Src/battery_curve.c Core/Src/soil_curve.c Core/Src/power_policy.c -lm && build/tests/t
   ```
3. Каждая исправленная **логика** покрыта тестом, и тест проверен мутацией: сломать
   условие → упал именно этот тест → вернуть. В отчёте перечислить мутации и какой тест упал.
4. Каждая находка из брифа закрыта одним из трёх способов: исправлена (коммит), не
   воспроизводится (почему), требует железа или решения владельца (что именно).

Чего в облаке нет: ARM-тулчейна и платы. Всё, что проверяется только на железе
(ток, тайминги, реальный USB), описать в отчёте как шаги для владельца.

## Коммиты

- Одна находка — один коммит (или несколько тесно связанных). Сообщение по-русски,
  как в истории репозитория: что меняется и почему, с номером находки в конце, например `(C2)`.
- Не коммитить `build/`, временные файлы, пропатченный дампером `main.c`.
- Перед пушем перечитать свой дифф целиком: нет ли случайных правок вне владения.

## Отчёт

Последним коммитом — файл `audit/reports/<ветка-без-префикса>.md`:

```
# Отчёт <правщик>
| Находка | Статус | Коммит | Тест / мутация |
|---|---|---|---|
## Нужны правки вне моего владения
## Проверить на плате (шаги для владельца)
## Остаточные риски
```
