БЛОК нет. ВАЖНО — два, оба про документацию и тесты, а не про код:

- обещание «поменял формат записи — LogFormat упадёт и без gcc» проверкой не подтверждается.

Код инструментов и прошивки дефектов не показал. Проверено и подтверждено:
- `--wipe` не стирает без полного, сверенного и разобранного образа. Цепочка условий —
  `read_data.sh:446-456`; второй дампер сам пересчитывает хеш (`dump_patch.py:133-165`).
  Мёртвая флеш (MISO в 0 или в 1) не может пройти как «пустая»:
  - MISO в 1 — `WaitBusy` срывается, `hash_ok = 0`;
  - MISO в 0 — образ из нулей, разбор говорит `foreign`, код 1.
- `main.c` после дампера возвращается байт в байт: `cp` из копии со сверкой `git hash-object`.
  `\r` в `$(...)` нигде не сравнивается: Python в подстановку не попадает, `src_sum` и
  `read_info` чистят CR.
- Мутации формата с gcc ловятся (11 из 12, таблица ниже).
- Табличный CRC даёт те же значения: таблица полубайтов стандартная, есть тест против побитового
  CRC в `test_main.c`, Python берёт CRC из `zlib`.
- V3: номер тома считается от UID во всех трёх ветках `VFat_Build` (`vfat.h:555-583`), от журнала
  не зависит.
- V1 и `bot_status = NORMAL`: статус ERROR держится до Reset Recovery. Подтверждено отдельным
  стендом на настоящем `usbd_msc_bot.c` (`insp5/bot/bench.c`):
  - некорректный CBW — STALL на обеих точках, OUT не взведён;
  - CLEAR_FEATURE на обе точки без Bulk-Only Reset — снова STALL, OUT не взведён, команду
    не принять;
  - после Reset: RECOVERY, CLEAR_FEATURE не порождает CSW;
  - следующий корректный CBW даёт NORMAL, TEST UNIT READY отвечает PASSED.

  Корректный CBW можно получить только после `MSC_BOT_Reset` или `MSC_BOT_SendCSW`: только они
  взводят OUT. Поэтому правка оркестратора статус ERROR не сбрасывает.

### F3 [МЕЛОЧЬ] `test_tools.py` на Windows без UTF-8 режима: 18 ERROR, а отчёт обещает «остальные OK»

**Где.** `tools/test_tools.py:63-66`, `run_tool`: `p.stdout.decode("utf-8")` без `errors`. Изъян
был и до П5в, но П5в добавил `UnpackUsb.*` и шаг 5 «под Windows … остальные OK»
(`p5c-tools.md`, «Проверить на плате»).

**Сценарий.** Дочерний `python` в канале на русской Windows пишет в cp1251. Смоделировал на
копии: `PYTHONIOENCODING=cp1251`, без gcc. Итог — 18 ERROR `UnicodeDecodeError`: PatchEol,
NanRanges, NewColumns, DsErrCodes, BatteryCurve, UnpackUsb ×6.

На английской Windows (cp1252) хуже: сами инструменты падают на `print` кириллицы с
`UnicodeEncodeError`. Тогда `read_data.sh` скажет «скопированный data.txt не сошёлся», хотя копия
верна.

**Что сделать**
- В `run_tool`: `env=dict(os.environ, PYTHONIOENCODING="utf-8")`.
- В инструментах (или в шапке `read_data.sh`) — `export PYTHONIOENCODING=utf-8`. Mintty по
  умолчанию UTF-8, так заодно уйдут кракозябры.

## Проверено и замечаний нет

**Windows / Git Bash**
- Буквы дисков перебираются явно.
- `cygpath -w` для путей программатора.
- Пути с пробелами взяты в кавычки (корень проекта, `TMPBIN`, `OUT`). Разбиение `$roots` по
  пробелам задевает только `/media/<имя с пробелом>` — несущественно.
- `seq`, `mktemp -u`, `chmod a-w` есть в Git Bash.
- MSYS сам переводит POSIX-пути в аргументах `python`.
- `.gitattributes` держит `*.sh` в LF. `dump_patch.py` читает и пишет с `newline=""`, вставка и
  откат сохраняют CRLF.
- Все не-ASCII символы в выводе инструментов есть в cp1251.

**Без gcc** `read_data.sh` (USB и SWD) не зависит ни от gcc, ни от `log_oracle.c`. Пропускаются
только PatchCompiles, Dumper, LogImage и сверка BatteryCurve (F2).

**Разбор против `log_record.h`**
- Смещения, виды, биты, little-endian (`<f`, `<I`) совпадают.
- `float` → `%.Nf` с `-nan`/`inf` как в printf; версия 1.
- Типы M/T/F/E; `data_old` — конкатенация TEXT, сверено оракулом.
- `import_pending` = `LogImport_Pending` (последняя годная запись — F или T).

**`--wipe`**
- Окончательный отказ при `FAIL` — неполный образ, незаконченный импорт, `foreign`, разбор ≠ 0.
- Отказ при `hash_ok ≠ 1`, при `--check` ≠ 0, при сбое `save_archive`.
- Второй дампер пересчитывает хеш и после сброса или повторного запуска отказывается
  (флеш уже другая).

**П5б+**
- V1: STALL IN только для READ10/12 (`DATA_IN`), OUT не взведён до CSW.
- `NORMAL` только в ветке корректного CBW.
- V3: UID через `HAL_GetUIDw*` (объявлены в `stm32f4xx_hal.h:251`), макрос в USER CODE
  (`usbd_storage_if.c:37-38`).
- V4: время файлов растёт с номером замера.
- CRC прежний.
